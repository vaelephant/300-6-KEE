# KEE Medical V1.0 知识治理与安全规范

> 文档编号：MKE-GOV-04
> 版本：1.0.0
> 状态：治理设计基线（待评审）

## 1. 治理目标

确保医学知识从来源接入、解析、抽取、融合、审核、发布、调用、更新和撤回全过程可控、可解释、可追溯。平台是医学知识管理与服务基础设施，不替代临床专业人员的诊疗责任。

## 2. 知识生命周期

建议状态流：

```text
registered
  -> ingested
  -> parsed
  -> extracted_candidate
  -> normalized
  -> conflict_checked
  -> machine_checked
  -> expert_review
  -> medical_administration_review
  -> published
  -> superseded / withdrawn / archived
```

各状态转换必须定义操作者/系统角色、前置条件、允许动作、失败原因和审计事件。失败任务可以重试，但不能把失败或未审核对象伪装成已发布知识。

## 3. 多级审核

### 3.1 机器自动校验

检查：
- 来源是否已登记、授权和符合白名单策略；
- 必要字段、证据定位和来源版本是否完整；
- 实体类型、关系谓词、编码和本体约束是否有效；
- 主张内部及与已知知识之间是否存在可检测矛盾；
- 知识发布时间、生效时间和更新状态；
- 规则表达式和输入输出结构是否合法。

机器通过仅代表自动校验规则通过，不代表医学权威性已获得专家确认。

### 3.2 科室专家初审

专家查看原文、定位、抽取结果、术语映射、限定条件、系统校验意见和冲突对比。可作出通过、驳回修改、退回重抽取等决定，并填写理由。

### 3.3 医务管理终审

对通过专业初审的知识进行合规性、安全性、适用范围和医院政策审核。批准后产生发布记录和明确的发布版本；拒绝或退回必须记录原因。

审核任务绑定对象版本快照。对象发生变更时，原审核不得自动沿用到新版本。

## 4. 知识冲突处理

冲突类型包括但不限于：
- 诊断标准冲突；
- 治疗方案冲突；
- 药品适应症、剂量或禁忌冲突；
- 检查指征冲突；
- 手术适应症冲突；
- 预后因素冲突；
- 不同人群、地区、版本或临床场景造成的表面冲突。

处理原则：
1. 先判断是否为真实矛盾，还是适用人群、时间、场景、定义不同。
2. 保存冲突双方的原始主张、来源版本、证据定位和限定条件。
3. 权威级别、循证等级和发布时间可作为辅助判断因素，但不得代替医学专家裁决。
4. 自动化系统只生成候选处置和理由，不应静默删除低优先级来源。
5. 专家决定可为并存、限定适用范围、采纳某主张、驳回或待补证。
6. 所有冲突处置可追溯、可复核、可重新打开。

## 5. 权威等级、循证等级与保密等级

这三个维度必须独立管理，不能合并成单一“知识等级”。

- **权威等级**：发布机构和来源类型，例如国家主管部门、国际指南组织、学术组织、公开文献、院内规范。
- **循证等级**：依据项目采用的循证评价体系记录，必须注明评价方法和体系版本。
- **保密/访问等级**：公开、内部、限制、机密等，由机构数据分类分级制度确定。

适用范围（疾病、人群、科室、地区、场景）是额外维度。来源权威不自动等同于对所有人群均适用。

## 6. 权限模型

建议采用 RBAC 与资源属性约束组合：

- RBAC：角色决定可执行的操作集合。
- 资源范围：租户、医院、科室、个人、知识空间。
- 属性策略：保密级别、知识状态、用途、调用方、时间限制。
- 最小权限：默认拒绝，显式授权。
- 职责分离：知识创建者、专业审核者和最终发布者按制度分离。
- 生命周期：申请、审批、授权、到期提醒、回收。

关键操作包括来源接入、文档下载、实体修改、映射确认、冲突裁决、规则发布、知识发布、撤回、批量导出和 API 客户端管理。

## 7. 多租户与患者数据边界

- 医院租户间数据默认隔离。
- 个人、科室、医院知识空间按显式授权共享。
- 公共医学知识与患者个人信息分域管理。
- 患者数据若进入后续业务流程，必须有独立的合法性基础、用途限制、脱敏/去标识化、访问审批和安全评估。
- 检索、向量召回、图谱遍历、缓存、导出和日志都必须执行相同授权边界。
- 演示环境使用公开或合成数据，不使用可识别真实患者数据。

## 8. 审计与安全事件

审计范围：
- 用户登录、授权和权限变更；
- 知识源配置、采集、下载和同步；
- 文件查看、导出、删除和版本更新；
- 抽取任务、模型/规则调用和结果修改；
- 术语映射、实体合并、冲突处置；
- 审核、发布、撤回和规则启停；
- 搜索、图谱查询、RAG 和 API 调用；
- 安全策略命中、异常访问和失败操作。

审计事件建议记录 actor、tenant、action、resource、resource_version、timestamp、request_id、source_ip（按安全政策）、result、reason 和必要的变更摘要。禁止记录明文密码、Token、密钥及不必要的患者敏感内容。

审计记录应具备防篡改保护、访问控制、备份和完整性校验。原需求提出审计日志至少保留三年；具体保留期限、存储位置和不可篡改实现须由法务、网安和医院制度确认。

## 9. 违规检测与告警

监测场景：
- 越权访问或跨租户访问；
- 限制级/机密级资源异常读取；
- 未授权修改已发布知识；
- 异常批量导出；
- API 高频调用、失败率异常或令牌滥用；
- 反复尝试访问无权资源；
- 审核流程绕过；
- 规则或知识版本未经审批被启用。

告警必须包含事件等级、对象、时间、调用者、策略命中原因、关联请求和处置状态。安全告警应进入调查、处置、关闭的闭环。

## 10. 医学知识安全边界

- 抽取置信度不是临床证据等级。
- 语义相似度不是医学等价关系。
- 模型输出不能自动成为权威指南内容。
- RAG 生成必须提供可核查的来源引用；无证据时应明确说明证据不足。
- 规则必须有版本、适用条件、测试样例、审批状态和停用机制。
- 临床应用上线前需进行独立验证、风险评估、临床治理审批和监测。
- 对付费医学数据库、期刊、图书和第三方术语资源，必须核实许可、复制、索引、展示和再分发范围。

## 11. 合规工作项

项目需求文件提及《中华人民共和国数据安全法》《医疗卫生机构网络安全管理办法》、等保三级和审计要求。实际项目应由法务、网络安全和医院信息部门依据项目所在地、数据类别、部署模式及最新有效规范进行合规适用性评估。

本文件是产品安全设计，不构成法律意见或等保测评结论。等保级别、测评范围、密码应用、日志期限和具体控制项均须专项确认。
