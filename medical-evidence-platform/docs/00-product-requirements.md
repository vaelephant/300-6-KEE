# KEE Medical V1.0 产品需求与范围

> 文档编号：MKE-PRD-00
> 版本：1.0.0
> 状态：架构设计基线（待评审）

## 1. 产品定位

产品名称继续为 **KEE（Knowledge Evolution Engine）**。医疗知识工程能力作为 KEE 的行业领域扩展，产品模块名称为 **KEE Medical**，不新建独立仓库，也不将 KEE 更名为其他产品。

KEE Medical 面向医疗卫生行业，建设多源医学知识采集、知识萃取、语义标准化、知识融合、本体管理、权威审核、临床规则、数据集标注规则、知识管理与知识服务能力。

平台的核心产出不是单纯的文档切片或向量集合，而是可管理、可审核、可追溯、可版本化、可供下游系统调用的医学知识资产。

## 2. 建设目标

1. 接入院内外多源异构医学知识，建立统一来源目录和元数据体系。
2. 从结构化、半结构化、非结构化及多模态资料中提取医学知识要素。
3. 建立医学实体、概念、关系、事实主张和证据之间的语义关联。
4. 实现跨来源术语标准化、实体消歧、属性补全和知识冲突识别。
5. 建立医学本体及其版本管理能力。
6. 建立机器校验、科室专家审核、医务管理终审的知识治理流程。
7. 将医学知识转化为可管理、可验证、可调用的临床规则和数据集标注规则。
8. 建立分级分类、租户隔离、细粒度权限和全链路审计。
9. 通过统一检索、图谱查询、规则服务、RAG 和 Open API 输出知识能力。
10. 与高质量数据集加工生产平台、资源与数据一体化调度管控平台及上层业务系统对接。

## 3. 目标用户与角色

| 角色 | 主要职责 |
|---|---|
| 平台管理员 | 租户、知识源、任务、用户、权限及平台配置 |
| 知识工程师 | 资料接入、解析任务、抽取结果整理、实体与关系维护 |
| 临床科室专家 | 本专业知识审核、冲突判断、修改建议 |
| 医务管理人员/知识管理委员会 | 合规终审、知识发布和撤回审批 |
| 数据集生产人员 | 查询和使用标注规范、术语映射与质量校验规则 |
| 科研人员 | 在授权范围内检索、分析和使用知识 |
| 外部系统/API 客户端 | 按授权调用标准知识服务 |

角色是业务职责定义，最终授权以租户、组织、科室、资源范围和操作权限的组合策略为准。

## 4. 业务范围：十个建设模块

### 4.1 多源异构医学知识统一采集

- 插件化知识源接入，覆盖数据库直连、RESTful/Web Service、文件导入和授权网页采集。
- 支持结构化、半结构化、非结构化资料。
- 接入范围包括国家临床指南、临床路径、ICD 疾病分类、手术操作分类、病案首页规范、医保诊疗规范、医学文献、循证证据、医学专著、专家共识、院内规范、专家经验、质控规则、医学术语与本体资源。
- 对接 SNOMED CT、LOINC、HL7/FHIR 及适用的国家医疗卫生信息标准时，必须先确认数据许可、版本、授权范围和实际可获得性。
- 建立来源元数据、链路监控、增量同步、版本管理和异常告警。
- 不修改原始知识源的底层架构和内容。

### 4.2 医学知识萃取与结构化管理

- 医学实体识别：疾病、症状体征、检查检验、药品、手术、解剖部位、病原体、基因/蛋白等。
- 医学关系抽取：疾病—症状、疾病—检查、疾病—药品、药品—不良反应、手术—适应症等。
- 临床事件抽取：诊断确认、治疗开始、手术执行、病情变化等事件及时间信息。
- 建立按临床科室、诊疗流程、知识类型、病种、场景和循证等级组织的知识目录。
- 管理知识实体、属性、同义词、编码和关系。
- 支持基于结构化知识生成诊断推理、治疗方案、用药审查、检查推荐、预后评估等训练指令模板。生成内容须标记来源和审核状态，不得默认作为临床指令执行。

### 4.3 知识融合与语义标准化

- 多来源知识差异和冲突识别。
- 知识优先级辅助判断，保留各来源原始主张和版本。
- ICD、SNOMED CT、LOINC、MeSH、院内术语等体系之间的映射管理。
- 实体消歧、同义词归一、缩写展开、跨语言映射。
- 实体属性补全及属性冲突管理。
- 自动候选匹配与人工确认相结合，保存映射方法、置信度、审核状态和依据。
- 不将“近似映射”或“关联映射”误当作概念等价。

### 4.4 医学知识本体与语义表示

- 建立疾病、症状体征、诊断、治疗、药品、检查检验、手术、解剖、并发症和预后因素等概念类。
- 定义对象属性、数据属性、领域/值域、约束和层级关系。
- 支持本体导入、编辑、校验、版本发布和变更影响分析。
- 兼容适用的 OWL/RDF 交换格式；内部映射以 KEE 实际支持能力为准。
- 支持知识单元向量化及语义索引；向量模型、维度、版本和索引状态必须可追溯。

### 4.5 医学知识权威校验与临床规则管理

- 建立机器自动校验、科室专家初审、医务部门终审的三级治理流程。
- 校验来源权威性、完整性、临床一致性、合规性和时效性。
- 建立诊断规则、用药规则、检查检验规则、手术规范规则、临床路径规则和病案质控规则。
- 规则具备适用条件、表达式、来源证据、版本、生效/失效时间、测试样例、审批记录和启停状态。
- 规则服务提供单条、批量、同步和异步调用能力。
- 规则在经过授权审批前，不得作为自动临床决策或医嘱执行依据。

### 4.6 数据集生产知识标注规则体系

- 医学实体标注规范：疾病、症状、体征、药品、检查、检验、手术、病史等。
- 临床关系标注规范：疾病—症状、疾病—检查、疾病—用药、检查—诊断、手术—适应症等。
- 多模态标注规范：病历文本、检验报告、DICOM 影像、病理切片等。
- 标注质量校验：一致性、准确性、完整性和编码合法性。
- 标注规则版本管理、示例、培训和历史版本追溯。
- 与数据集生产平台共享术语、实体定义、关系谓词、规则和质量校验依据。

### 4.7 知识分级权限管控与全链路审计溯源

- 按权威级别、保密等级、适用范围和循证等级分类。
- 支持公开、内部、限制、机密等访问级别；具体等级须由医院制度和数据分类分级要求确认。
- 基于角色、组织、科室、资源和操作建立细粒度权限。
- 权限申请、审批、授权、到期回收。
- 记录接入、萃取、编辑、映射、审核、发布、撤回、检索、调用、导出等事件。
- 异常访问和违规操作识别、告警与调查闭环。
- 审计保留期限按适用法律法规、医院制度和项目合同确认；原需求提出至少三年，实施前应完成合规确认。

### 4.8 知识管理平台

- 文档知识：PDF、DOC、DOCX、ODF 等资料上传、分类、解析、分片、版本和检索。
- 多媒体知识：视频、语音、音频元数据、转写、时间戳摘要和跨模态关联。
- 量表知识：量表元数据、题目、题型、计分、版本和发布审批。
- 科普文章：导入、编辑、分类、版本和发布审批。
- 知识图谱：本体 Schema、实体、属性、关系、候选三元组和审核。
- 规则知识：IF-THEN、决策树、条件、动作、优先级和版本。
- 多层级知识空间：个人、科室、医院，支持逐级申请共享和审批。
- 功能权限与数据权限分离管理。

### 4.9 知识服务平台

- 跨知识类型统一查询。
- 关键词检索、语义向量检索、混合检索和跨模态检索。
- 知识图谱可视化查询、路径搜索、子图展开和多跳推理。
- 临床规则检索、匹配、推理和结构化结果返回。
- RAG 检索、上下文构建、来源与循证等级展示。
- RESTful 知识检索、图谱、规则和 RAG 服务接口。
- API Key/Token 认证、授权范围、限流、监控和调用审计。

### 4.10 业务平台服务对接

- 向高质量数据集加工生产平台提供术语映射、语义对齐、标注规则、临床逻辑校验、知识向量检索等能力。
- 与资源与数据一体化调度管控平台对接算力、存储资源及数据目录/元数据。
- 为临床辅助决策、智能病案质控、智慧运营和智慧科研提供知识服务。
- 建立 API 注册、版本发布、测试、启停、废弃、监控和告警机制。
- 支持知识更新通知和下游依赖方变更订阅。

## 5. 关键业务对象

平台必须区分以下对象：

- **Source**：外部或内部知识来源及其接入配置。
- **Document/Asset**：原始文档或多模态文件及版本。
- **Content Block**：解析后的页、段、表格、图像区域、音视频片段等内容单元。
- **Entity**：规范化医学实体。
- **Concept**：来自外部术语体系或本体的标准概念。
- **Relation**：实体间具有明确语义类型的关系。
- **Assertion**：具有上下文、适用条件和时间范围的知识主张。
- **Evidence**：支持、反驳或限定主张的来源证据及定位。
- **Ontology**：版本化的类、属性、约束和映射。
- **Rule**：可测试、可审批、可版本化的规则定义。
- **Annotation Guideline**：标注任务使用的规则、边界和示例。
- **Review Decision**：审核者、结论、理由、时间和所审对象版本。
- **Audit Event**：用户或系统对资源执行操作的审计记录。

## 6. 非目标与边界

- KEE Medical V1.0 不替代医生作出诊断或治疗决定。
- 不将未经审核的模型抽取结果自动发布为权威知识。
- 不在未核实许可的情况下批量抓取或存储付费医学数据库全文。
- 不在首期演示中使用可识别患者个人信息。
- 不在缺乏性能证据时默认引入独立图数据库、向量数据库或搜索集群。
- 不重写 KEE Rust 核心，也不整体推翻现有医疗前后端。
- 原方案中的指标须作为待验证目标管理，不得作为现有能力宣传。

## 7. 业务验收主线

首个端到端场景建议采用经授权的公开医学指南资料：

来源注册 → 文件导入 → 解析定位 → 知识抽取 → 术语映射 → Assertion 与 Evidence 建立 → 冲突识别 → 专家审核 → 知识发布 → 混合检索/图谱查询 → 返回来源证据。

该闭环仅验证知识工程能力，不构成临床诊疗验证。
