# KEE Medical V1.0 研发路线与验收标准

> 文档编号：MKE-PLAN-05
> 版本：1.0.0
> 状态：计划基线（待评审）

## 1. 实施原则

- 当前工作阶段只完成开发设计文档，不提交业务代码、迁移脚本、前端页面或部署脚本。
- 文档评审通过后，再根据代码审查结果拆分实施任务。
- 所有功能状态以代码、测试和运行证据为准，不以规划文档或 README 描述代替验收。
- 每阶段必须有可检查交付物、测试证据和明确的未完成项。
- 优先完成端到端闭环，再扩展更多病种和数据模态。

## 2. 阶段规划

### P0：现状审计与需求基线

交付：
- KEE Rust crates 能力清单及 API 盘点。
- 医疗平台前后端、数据库、迁移、测试、部署审查报告。
- 现有数据契约与本文件数据模型差异表。
- 外部标准和知识源许可清单。
- 风险、技术债和能力缺口清单。

验收：
- 每项复用能力都有代码路径、接口或测试证据。
- 明确现有能力、部分能力、缺失能力，不以目录存在推断功能完成。

### P1：架构与领域设计

交付：
- 产品需求、总体架构、领域数据模型、API 集成、治理安全、路线验收文档。
- 架构决策记录（ADR）。
- 现有系统兼容性和数据迁移策略。
- 领域对象与 API 契约评审记录。

验收：
- 业务范围覆盖原方案 2.3.1—2.3.10。
- Entity、Relation、Assertion、Evidence、Ontology、Rule 定义无歧义。
- 双时态和证据链规则明确。
- 服务边界、租户隔离、审核和发布流程明确。
- 未决事项均有负责人或后续决策节点。

### P2：知识源接入与多模态解析

规划能力：
- 知识源注册、连接测试、授权信息、健康监控。
- 文档/资产上传、版本、哈希、元数据。
- PDF/Office/HTML/XML/JSON 等解析适配。
- 章节、段落、表格、图像区域和媒体时间戳定位。
- OCR、音视频转写及 DICOM 专业影像处理能力按许可和技术评审分期实施。

验收建议：
- 可导入经授权的样例资料并保留原始文件版本。
- 解析结果可定位回原始页/段/表或媒体时间戳。
- 重复文件可识别，重新解析不覆盖历史结果。
- 任务具备状态、失败原因、重试和审计。
- 对无法解析的内容明确报告，不静默丢弃。

### P3：医学知识萃取、语义标准化与本体

规划能力：
- 实体、关系、事件、属性抽取。
- 术语候选召回、编码映射和人工确认。
- Entity/Concept/Relation/Assertion/Evidence 关联。
- 医学本体包、版本、类、属性、约束和导入。
- 冲突候选识别、属性补全和消歧。

验收建议：
- 抽取结果能追溯到原文定位和模型/提示版本。
- 映射区分 exact、broader、narrower、related。
- 低置信或多义候选进入审核，不自动错误合并。
- 本体版本可比较、发布和回溯。
- 冲突双方及上下文均保留。

### P4：知识治理、规则与标注规范

规划能力：
- 机器校验、科室专家初审、医务终审。
- 冲突处理、发布、撤回和版本管理。
- 临床规则配置、测试、审批和调用。
- 实体、关系、多模态标注规则。
- 标注一致性、准确性和完整性检查。

验收建议：
- 未审核知识不能进入正式发布检索范围。
- 审核任务绑定具体版本，内容变化后重新审核。
- 规则发布必须通过测试和审批。
- 标注规范有版本、示例和适用范围。
- 所有审核和规则操作有审计记录。

### P5：知识服务与平台集成

规划能力：
- 关键词、语义、混合和跨模态检索。
- 图谱路径和受控推理。
- 带来源引用的 RAG。
- 知识、规则、标注规则 Open API。
- 与数据集平台、调度管控平台和上层业务系统集成。
- API 生命周期、限流、监控、审计和版本通知。

验收建议：
- 搜索结果只返回调用者有权访问的知识。
- 结果带来源版本、证据定位、审核状态和适用范围。
- 无证据时明确返回证据不足。
- API 契约测试通过，调用方可按版本稳定集成。
- 下游可感知知识更新、撤回和规则版本变化。

## 3. 首个端到端演示

建议以授权使用的公开医学指南或明确许可的样例文档为输入，演示以下链路：

1. 管理员登记知识来源并记录许可/授权信息。
2. 上传指南文件，生成资产哈希和文档版本。
3. 解析章节、页码、段落、表格等内容定位。
4. 抽取疾病、检查、治疗等候选实体和关系。
5. 将候选术语映射到指定标准体系，展示映射类型和依据。
6. 生成带限定条件的知识 Assertion。
7. 将 Assertion 与原文 Evidence 定位关联。
8. 检测潜在冲突并展示冲突双方。
9. 专家审核并给出决定及理由。
10. 经授权终审后发布知识版本。
11. 通过统一检索或图谱查询返回知识及证据出处。

演示中必须清晰区分模型候选、审核通过知识和正式发布知识。

## 4. 指标管理

原需求方案提出了部分准确率、召回率、标注精度和响应时间目标。这些指标应进入后续专项测试计划，不得在没有测试数据时宣称达成。

| 指标方向 | 原需求/规划目标 | 验证要求 |
|---|---|---|
| 医学实体识别 | 准确率不低于 95%，召回率不低于 90% | 明确语料、实体类型、标注规范、样本量和计算口径 |
| 关系抽取 | 准确率不低于 90% | 明确关系类型、正负样本和评估方法 |
| 术语映射 | 原方案提出语义匹配与规则分层覆盖目标 | 建立标准答案集，分别统计 exact/近似/关联映射 |
| 多模态标注 | 原方案提出影像、病理等精度要求 | 按模态、任务和标注工具制定独立评测 |
| 检索 | 原方案提出毫秒级向量检索期望 | 明确语料规模、硬件、并发、过滤条件和 P50/P95/P99 |
| API 服务 | 需监控成功率、调用频次和延迟 | 明确 SLA、负载模型、超时与降级策略 |
| 治理 | 未审核知识不得发布 | 通过权限与状态机测试验证 |
| 溯源 | 每条发布知识可回到来源和定位 | 抽样核验完整证据链 |

## 5. 测试策略

- 单元测试：领域模型、状态机、时间逻辑、映射规则。
- 集成测试：FastAPI—KEE Adapter—KEE 服务—数据库/对象存储。
- 契约测试：OpenAPI、错误码、请求/响应兼容。
- 权限测试：跨租户、跨科室、不同保密等级、导出和检索过滤。
- 数据质量测试：重复、缺失、冲突、异常编码、无效定位。
- 回归测试：来源更新、模型升级、本体升级、规则版本变更。
- 安全测试：认证、授权、注入、文件上传、密钥保护和审计。
- 性能测试：任务吞吐、检索延迟、索引构建、并发和资源消耗。
- 医学专家评估：抽取正确性、术语映射、知识适用范围和冲突处置。

## 6. 主要风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 第三方知识源许可不清 | 无法合法采集/展示 | 接入前完成许可登记 |
| 医学标准版本差异 | 错误映射或过时知识 | 记录系统 URI、版本和发布日期 |
| 模型抽取幻觉 | 错误知识进入库 | Evidence 强制关联、人工审核 |
| 语义冲突被错误自动消解 | 临床风险 | 保留并存主张，专家裁决 |
| 多租户权限遗漏 | 数据泄露 | 检索、图谱、缓存、导出全链路测试 |
| KEE API 能力不匹配 | 适配成本增加 | P0 能力盘点和接口差距评审 |
| 多模态处理成本高 | 资源与交付延期 | 按模态分阶段建设和资源测算 |
| 规则适用范围不完整 | 错误触发 | 强制条件、版本、测试和审批 |

## 7. 待决策事项

以下事项需在进入对应开发阶段前明确：

1. 首期部署目标：单医院、本地化多医院，还是 SaaS 多租户。
2. 首期病种范围：建议先以肝癌作为演示领域，但需确认权威资料和专家审核资源。
3. 医学术语标准的实际授权版本和中文资源来源。
4. 第三方指南、文献和循证数据库的接入许可及采购边界。
5. 多模态范围：首期是否包含 DICOM、病理切片和音视频。
6. 规则引擎的表达语言和执行隔离策略。
7. 医疗知识发布委员会、科室专家和终审责任人的组织流程。
8. 审计留存、数据分类分级、等保与密码合规适用要求。
9. KEE 当前图谱、向量、全文检索和推理接口的实际能力差距。
10. 性能、并发、容量和可用性目标。
