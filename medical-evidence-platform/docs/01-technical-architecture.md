# KEE Medical V1.0 总体技术架构

> 文档编号：MKE-ARCH-01
> 版本：1.0.0
> 状态：架构设计基线（待评审）

## 1. 架构目标

在保护现有 KEE Rust 引擎和医疗证据平台投入的前提下，形成职责清晰、可独立演进的医疗领域扩展。架构采用“医疗领域服务 + KEE 知识引擎 + 统一数据与资产管理”的方式，不将医疗业务逻辑直接耦合到 KEE 内部数据库结构。

## 2. 总体逻辑架构

```text
用户 / 医院业务系统 / 数据集生产平台 / 调度管控平台
                         |
                  API Gateway / Auth
                         |
          KEE Medical Web Console (现有前端演进)
                         |
              Medical Domain Services
      +------------------+-------------------+
      |                  |                   |
  Source & Ingest    Extraction          Governance
  Terminology        Ontology workflow   Rules & Annotation
      |                  |                   |
      +------------ KEE Adapter ------------+
                         |
                 KEE Rust Engine
       Ontology / Temporal Knowledge / Entity Resolution
       Reasoning / Conflict Detection / Hybrid Search
                         |
       +-----------------+-------------------+
       |                 |                   |
  PostgreSQL       KEE-managed index     Object Storage
  domain metadata  graph/search/vector  source & media files
```

此图为逻辑职责图，不代表所有模块已在仓库实现。实际部署拓扑、进程数量和数据归属须在工程审查后确认。

## 3. 系统边界

### 3.1 KEE Rust 核心

原则上复用仓库现有 crates 所承载的能力，包括知识存储、摄入、抽取、推理、搜索、LLM 接入和服务接口。医疗项目不得未经评审修改核心语义或直接依赖其内部表结构。

医疗扩展需要的能力若 KEE 暂不支持，应先形成能力差距记录、接口提案和性能验证，再决定扩展核心或由领域服务补足。

### 3.2 Medical Domain Services

优先演进 `medical-evidence-platform/back` 现有 FastAPI 服务。其职责包括：

- 医疗来源目录和接入配置。
- 医疗文件、证据锚点和解析任务管理。
- 医学知识契约、审核流程和领域元数据。
- 术语映射任务、标注规范和临床规则业务管理。
- 租户/医院业务授权及对外 API。
- 与 KEE Adapter 的编排和数据转换。

不得在未经现有代码审查前假定已有功能或新增平行实现。

### 3.3 KEE Adapter

Adapter 是领域服务与知识引擎之间的防腐层：

- 将医疗 Entity、Relation、Assertion、Evidence、Ontology 转换为 KEE 支持的表示。
- 封装 KEE API、错误码、重试、超时和幂等处理。
- 负责标识映射、版本映射、来源引用映射。
- 隔离 KEE 版本变化对医疗业务的影响。
- 记录请求 ID、关联 ID、引擎版本和处理结果。
- 不允许领域服务直接写 KEE 内部数据库。

### 3.4 Web Console

优先复用 `medical-evidence-platform/front`。规划功能包括知识源管理、文档资产、解析任务、知识目录、实体/关系、本体工作台、冲突工作台、专家审核、规则管理、标注规则、图谱探索、统一检索、API 管理和审计查询。

UI 具体信息架构与视觉规范另行评审，不在本架构文档中预设现有页面已经具备这些能力。

## 4. 技术选型原则

| 层 | 优先选型 | 说明 |
|---|---|---|
| 前端 | 现有 Next.js 工程 | 先审查当前版本和组件体系，不因规划升级而直接改版本 |
| 医疗业务 API | 现有 FastAPI/Python | 复用已有业务模型和证据服务 |
| 知识引擎 | KEE Rust | 复用现有引擎能力 |
| 业务数据库 | PostgreSQL | 业务元数据、流程、权限、审核 |
| 向量检索 | 优先评估 KEE 当前实现 | 不默认另建 Milvus/Pinecone |
| 全文检索 | 优先评估 KEE/Tantivy | 不默认另建 OpenSearch |
| 原始文件 | S3 兼容对象存储 | 保存原始文件、派生文件和多媒体资产 |
| 异步任务 | 先评估现有任务机制 | 只有任务量、重试和并发需求证明必要时再选 Celery/Redis 等 |
| API 契约 | REST/OpenAPI | 统一版本、错误、认证和幂等规范 |
| 事件/通知 | 事务发件箱或可靠事件机制 | 保障知识更新和下游通知一致性 |

具体依赖版本、运行环境和部署形态以现有仓库检查及兼容性验证为准。

## 5. 数据职责与一致性

- PostgreSQL 领域 Schema 保存医疗业务工作流、来源元数据、审核状态、规则管理和访问控制等数据。
- KEE 管理其知识引擎自身的数据结构、图谱、索引和推理状态。
- 对象存储保存原始文件及派生的图像、音频、视频、OCR 和解析产物。
- 业务数据库与 KEE 不共享写表事务；跨服务更新采用 Outbox/任务状态/幂等重试等可靠集成模式。
- 原始资产不可因重新解析而被覆盖；每次解析和抽取均关联资产版本、解析器版本和模型版本。
- 证据定位需可回到原始文件的页码、段落、表格、坐标区域或媒体时间戳。

## 6. 多模态处理架构

统一资产管线建议包括：

1. 接入：来源授权检查、文件类型识别、哈希去重、病毒/安全扫描策略。
2. 预处理：格式转换、页面渲染、OCR、表格提取、音视频转写、DICOM 元数据解析。
3. 内容分块：按章节、段落、表格、图像区域和时间片段生成可定位内容单元。
4. 抽取：识别实体、关系、事件、属性、条件和候选主张。
5. 关联：将抽取结果关联到来源版本和证据定位。
6. 治理：标准化、冲突识别、人工审核和发布。
7. 索引：全文、向量、图谱索引，并记录索引版本。
8. 服务：统一检索和授权范围内的知识调用。

DICOM、病理切片等专业影像的处理能力需要独立的格式、脱敏、存储和标注规范评审，不应把普通 OCR 管线视为可直接处理医学影像。

## 7. 环境与部署原则

- 开发环境优先支持现有项目已验证的 macOS/Linux 开发方式。
- 测试环境提供隔离数据库、对象存储和模型端点。
- 医院部署支持院内部署、网络隔离和可配置的模型服务端点。
- 密钥、数据库口令和 API Token 不得提交到 Git。
- 生产部署必须提供备份、恢复、迁移前检查、日志和监控方案。
- 容器化、信创适配、国产数据库/操作系统兼容等需求需要结合目标医院清单另行形成兼容性矩阵。

## 8. 架构决策记录（ADR）

| 编号 | 决策 | 理由 | 后续验证 |
|---|---|---|---|
| ADR-001 | 项目仍叫 KEE，医疗扩展叫 KEE Medical | 保留品牌与核心引擎边界 | 产品命名评审 |
| ADR-002 | 复用现有医疗平台，不重建仓库 | 保护既有资产 | 代码与依赖审查 |
| ADR-003 | 以 Adapter 连接医疗服务和 Rust 引擎 | 降低耦合 | API 能力验证 |
| ADR-004 | 不默认新增图/向量/搜索数据库 | 避免重复基础设施 | 基准测试后复议 |
| ADR-005 | 原始资产、证据、知识主张分离 | 支持追溯和版本 | 数据模型评审 |
| ADR-006 | 未审核知识不进入正式发布状态 | 医疗知识治理要求 | 审批流程测试 |

## 9. 架构风险

- 现有医疗平台和 KEE 可能存在数据模型或身份体系差异。
- KEE 当前 API 是否覆盖医疗场景所需的所有操作，必须逐项验证。
- 多模态解析可能涉及授权、隐私、格式兼容和较高计算成本。
- 双时态、来源版本和知识主张的语义必须在数据模型阶段统一。
- 下游系统依赖知识版本时，需要设计兼容与通知机制。
